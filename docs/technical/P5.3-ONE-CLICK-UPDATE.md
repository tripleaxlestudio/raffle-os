# P5.3 One-Click Update

Status: Slices 1 through 4 implemented for owner review. No version bump,
release installer build, real upgrade, tag, or release is part of these slices.

## Approved architecture and release reality

The approved end state is:

```text
Browser UI
  -> loopback update API
  -> Node update manager
  -> WinForms launcher
  -> detached Kocokan.Updater.exe
  -> Inno Setup
  -> relaunched Kocokan
```

The public v0.1.0 build contains only the P5.2 update checker and cannot start a
native update. Users on v0.1.0 will install v0.1.1 manually. v0.1.1 is the
bootstrap updater release. The first official one-click acceptance is
v0.1.1 -> v0.1.2.

Updates remain user-confirmed. There is no startup download or silent
background installation. A later safety slice must block installation whenever
an Audience is connected, including standby.

## Slice 1 implementation

Slice 1 adds four server-side modules:

- `release-resolver.ts` reads only the fixed public GitHub latest-release API,
  accepts an exact stable `vX.Y.Z` tag newer than the current version, and
  resolves one exact installer plus one `checksums.txt` asset.
- `checksum-parser.ts` accepts the release contract `<64 hex><two spaces><name>`
  and returns one case-normalized digest for the exact installer name.
- `download-manager.ts` follows a bounded HTTPS-only GitHub-host redirect
  chain, streams to `.part`, reports determinate or indeterminate progress,
  validates byte count and streaming SHA256, and atomically renames only after
  verification. A failed operation removes its partial file.
- `update-api.ts` owns the single in-memory preparation job and exposes only
  safe state. It never returns an asset URL, checksum, filesystem path, token,
  or exception detail.

The existing standalone server remains bound exclusively to
`127.0.0.1:47882`. Its display WebSocket and asset contracts are unchanged.

## Trust boundary and local API

Available routes:

| Method | Route | Behavior |
| --- | --- | --- |
| `GET` | `/api/update/capabilities` | Returns environment and whether preparation/install are supported. |
| `POST` | `/api/update/bootstrap` | Returns the per-runtime mutation token only to the canonical same-origin application. |
| `POST` | `/api/update/prepare` | Validates the request, resolves the release, downloads, and verifies the installer. |
| `GET` | `/api/update/status` | Returns the safe public job state and progress. |
| `POST` | `/api/update/install` | Accepts the exact ready version once and requests a private launcher handoff. |
| `GET` | `/api/update/result` | Returns one consumed bounded result from the preceding updater run, or `null`. |

The only accepted prepare body is:

```json
{"version":"0.1.2"}
```

Unknown fields, `url`, `path`, malformed versions, non-JSON bodies, absent or
foreign Origin, an invalid mutation token, and concurrent jobs are rejected.
The body is limited to 1 KiB. The version, repository, asset names, destination
layout, redirect hosts, and final filenames are controlled by native code.

Mutating requests require `X-Kocokan-Update-Token`. The token is available only
from `POST /api/update/bootstrap`, which requires the exact canonical Origin
and returns `Cache-Control: no-store`. It is not present in the capability or
status payload. The Slice 3 browser client keeps it in a private service field
in memory only; localStorage, sessionStorage, IndexedDB, cookies, and logs are
not used.

## Capability model

The capability enum is `development | portable | installed`.

The launcher is now the capability authority. Installed mode requires all of:

- the stable Inno uninstall key
  `{5F39F696-B62A-49CA-A090-366BE7E49213}_is1`;
- a nonempty `InstallLocation` in HKLM;
- a canonical path match between `InstallLocation`, `AppContext.BaseDirectory`,
  and the running launcher executable directory.

The current admin/x64 installer writes HKLM Registry64. The detector checks
HKLM Registry64 first and HKLM Registry32 for view compatibility. An audit of
the current installation found the entry only in HKLM Registry64. HKCU 32/64
were empty and are deliberately not accepted as authority because the current
installer is `PrivilegesRequired=admin`. Missing, malformed, inaccessible, or
mismatched registry data returns `portable`.

Portable capability keeps `prepareSupported=false` and
`installSupported=false`. A verified installed launch activates preparation;
installation remains disabled in Slice 2.

The Vite development server does not expose this native API; the future browser
client must treat that as `development` and keep installation disabled.

## Launcher to runtime bootstrap

For every Node runtime start, the launcher generates 32 bytes using
`RandomNumberGenerator.GetBytes` and encodes them as 43-character unpadded
base64url. Tokens are never reused, persisted, registered, or logged.

Capability and token are passed as child-scoped environment variables:

```text
KOCOKAN_UPDATE_CAPABILITY=portable|installed
KOCOKAN_UPDATE_TOKEN=<43 character base64url>
```

Environment variables were chosen instead of CLI arguments so the token is not
present in ordinary process command-line listings. The launcher removes any
inherited values before setting its authoritative values. The runtime consumes
and deletes both variables once at startup. Missing or invalid metadata falls
back to portable. The install root is not sent because Slice 2 preparation only
needs `%LOCALAPPDATA%`; no filesystem location is exposed to the browser.

## Job contract

Public states are:

```text
idle -> preparing -> downloading -> verifying -> ready-to-install
                                                   |
                                                   +-> installing (reserved)
any active state -> error
```

Only one job may be active. A second prepare request returns HTTP 409. Slice 1
stops at `ready-to-install`; there is no install route or handoff behavior yet.
An error may be retried. Public errors are deliberately coarse:
`release-unavailable`, `release-invalid`, `download-failed`,
`checksum-invalid`, or `storage-failed`.

## Download boundaries

- Root contract: `%LOCALAPPDATA%\Kocokan\updates\<version>\`.
- Temporary name: `Kocokan-Setup-X.Y.Z.exe.part`.
- Final name: `Kocokan-Setup-X.Y.Z.exe`.
- Installer size: 1 MiB through 512 MiB.
- Checksum response: maximum 1 MiB.
- Redirects: at most five and HTTPS only.
- Allowed download hosts: `github.com`, `objects.githubusercontent.com`, and
  `release-assets.githubusercontent.com`.
- The initial asset URL must be the exact official repository/tag/filename
  release path.
- Default installer timeout: 15 minutes; checksum timeout: 30 seconds.

The server-side default service is ready to receive the update root later, but
the runtime does not activate it while capability is conservative.

## Slice 3 browser preparation flow

`LocalUpdateClient` separates the existing public GitHub P5.2 release check from
native preparation. A missing or non-JSON native capability endpoint is treated
as development mode without surfacing request noise. Portable and development
show the installed-build requirement; only an installed capability may offer
`Update Sekarang`.

The mutation token is bootstrapped only when preparation is requested. A 401 or
403 clears it and permits exactly one re-bootstrap; a second authorization
failure stops safely. Status polling uses a 750 ms cadence and stops on
`ready-to-install`, error, unmount, or runtime unavailability. The UI exposes
determinate progress when a percentage exists and an indeterminate progress bar
otherwise. Native error categories are mapped to Indonesian operator copy; raw
response bodies and exceptions are never displayed.

Slice 3 deliberately stopped at `Siap dipasang`. Slice 4 enables the install
control only when the installed launcher also exposes a private stdio handoff.

## Authoritative safety gate

Immediately before preparation, the production authority rereads IndexedDB
storage health, the active Event, Live sessions, recovery decisions, command
receipts, redraw requests, and presentation checkpoints. It also reads the
current Operator publisher diagnostics. Any active Audience subscriber blocks
preparation, including a subscriber showing standby. Missing publisher
diagnostics for a configured display are ambiguous and therefore block.

The gate fails closed for unreadable workspace state, drawing or
pending-confirmation, conflicting or unresolved recovery, started/unknown
receipts, active redraw recovery, and countdown, rolling, reveal, or
pending-handoff checkpoints. Routes and cached UI labels are not inputs.

## Global update lock

The first safe read is followed by synchronous acquisition of the shared update
lock and a second authoritative read. Acquiring the tentative lock before that
second read closes the check-to-prepare race: new draw commands, redraw requests,
and redraw starts are rejected while the read is in flight and throughout
preparation.

The lock is process-memory state. It is released when preparation fails, native
runtime access is lost, or an explicit future reset/abort invokes `release`.
It remains active at `ready-to-install` until a future install handoff or reset.
A runtime restart naturally clears both the server job/token and browser lock.
Navigation and non-critical settings remain available.

## Slice 4 install handoff

The install request accepts only `{ "version": "X.Y.Z" }`, requires the
same-origin mutation token, an installed capability, a verified
`ready-to-install` job for that exact version, and a single request. It returns
before shutdown begins. Runtime stdout then emits only the bounded message
`{"type":"update-install","version":"X.Y.Z"}`.

The launcher parses that message strictly: duplicate, missing, malformed, or
extra fields are rejected. It derives the installer path itself under
`%LOCALAPPDATA%\Kocokan\updates\<version>\`, verifies the exact installer and
packaged updater exist, copies the single-file updater beside the installer,
and launches it outside the launcher ChildJob. No URL or caller-selected path
crosses the browser or stdout boundary.

The updater accepts only launcher PID, version, and install root arguments. It
verifies that it is executing from the exact version directory, then waits up
to 30 seconds for the launcher PID, `Local\Kocokan.Pilot.47882` mutex, and port
47882 to be released. The launcher requests the existing graceful stdin
shutdown. A forced runtime stop aborts the updater and restores the local
runtime when possible, so installation never proceeds from the forced-stop
path.

Inno Setup is invoked with `/SP- /SILENT /SUPPRESSMSGBOXES /NORESTART
/NOCLOSEAPPLICATIONS /NORESTARTAPPLICATIONS`; `/VERYSILENT` is deliberately
not used. Exit 0 is success, Inno exit 2 or 5 and Windows UAC cancellation are
cancelled, and other nonzero exits are failures. The updater writes only
`version`, `result`, and `timestamp` to an atomic
`%LOCALAPPDATA%\Kocokan\updates\last-update-result.json`, then attempts one
launcher relaunch for every terminal result. The next runtime consumes that
file once and the About UI reports success, cancellation, or failure.

The production safety authority is read twice again immediately before the
install request while the global update lock remains active. Any newly unsafe
draw, recovery, presentation, or Audience state blocks the handoff.

Startup cleanup is intentionally narrow: only the exact stale
`Kocokan-Setup-<same-version>.exe.part` file in an immediate semantic-version
directory is removed. Completed version directories and unrelated `.part`
files are preserved.

## Remaining limitations

Not implemented yet:

- signed installer/publisher authenticity.
- old completed update directories are retained; no retention policy is
  implemented.
- the real installed v0.1.1 to v0.1.2 upgrade remains an owner acceptance gate.
